# Workflows

ComfyUI **API-format** graphs for the three modes, used by `worker/handler.py`.
They are copied to `/runpod-volume/workflows/` (the handler loads
`/runpod-volume/workflows/<mode>.json`). Core ComfyUI nodes only: the
ComfyUI-LTXVideo pack is installed in the worker image but no node from it is used.

Workflow version: 1

## Files

| File | What |
|---|---|
| `t2v.json`, `i2v.json`, `v2v.json` | Default: two-stage distilled (half-size generate, x2 latent upscale, short refine) |
| `single-stage/{t2v,i2v,v2v}.json` | Fallback: one full-size 8-step pass, no upscaler. Same titles and contract. |

Two-stage is the default because it matches the Comfy-Org template and, on paper, costs
about the same GPU time as one full-size pass (8 steps at 1/4 of the pixels plus 3 at full
size). **That is unmeasured.** If the real-GPU test shows two-stage losing on time or VRAM,
copy `single-stage/*.json` over the top-level files and sync the volume. Nothing else changes.

Derived from the Comfy-Org workflow templates `video_ltx2_5_t2v` and `video_ltx2_5_i2v`
(github.com/Comfy-Org/workflow_templates), with these deliberate differences: the image is fitted
with `ImageScale` instead of `ResizeImageMaskNode`, the bypass toggles are hard-wired per mode,
no prompt enhancer, both `RandomNoise` nodes use `SEED`, output is explicit mp4/h264.

## Version marker

`Workflow version: 1` (line above). Workflows live on the network volume and the handler lives in
the image, so a contract change must ship as one release: bump this number, rebuild the image
if the handler changed, and re-sync `workflows/` to the volume. The number is also in the
output file name prefix (`video/LTX_2.5_<mode>_wf1_*.mp4`), so a mismatch is diagnosable from
ComfyUI's output folder and logs. (A top-level `"version"` key in the JSON is not possible: the
handler requires every top-level entry to be a node, and `/prompt` rejects it.)
`scripts/check_workflows.py` fails if the prefix and this number differ.

## Handler contract (titles)

The handler fills nodes by `_meta.title`, never by node id. Ids below are those generated by
`scripts/build-workflows.py` for the two-stage files and are informational.

| Title | class_type | Field set | Mode | Wired to |
|---|---|---|---|---|
| `PROMPT` | `CLIPTextEncode` | `text` | all | `LTXVConditioning.positive` |
| `NEGATIVE` | `CLIPTextEncode` | `text` | all | `LTXVConditioning.negative`; keeps its default text when the caller sends none. CFG is 1, so it has almost no effect; the UI hides the field |
| `WIDTH`, `HEIGHT` | `PrimitiveInt` | `value` | all | final size; stage 1 uses `ComfyMathExpression "a/2"` |
| `FRAMES` | `PrimitiveInt` | `value` | all | `EmptyLTXVLatentVideo.length`, `LTXVEmptyLatentAudio.frames_number` |
| `FPS` | `PrimitiveFloat` | `value` | all | `LTXVConditioning`, `LTXVEmptyLatentAudio`, `CreateVideo` |
| `SEED` | `PrimitiveInt` | `value` | all | both `RandomNoise` nodes |
| `INPUT` | `LoadImage` | `image` | i2v | `ImageScale` -> `LTXVPreprocess` -> `LTXVImgToVideoInplace` (x2) |
| `INPUT` | `LoadVideo` | `file` | v2v | `Video Slice` -> `GetVideoComponents` -> `ImageFromBatch` -> `ImageScale` -> `LTXVAddGuide` (x2) |
| `OUTPUT` | `SaveVideo` | (found by title) | all | exactly one per file; `format: mp4`, `format.codec: h264` |

Node ids (two-stage): t2v 1-5 loaders, 6-10 WIDTH/HEIGHT/FRAMES/FPS/SEED, 11 PROMPT,
12 NEGATIVE; the rest follow in the build order. Look up ids with
`python3 -c "import json;[print(i,n['_meta']['title']) for i,n in json.load(open('workflows/t2v.json')).items()]"`.

### Required handler behaviour (not in this branch)

* **Width and height must be multiples of 64.** Stage 1 runs at half size and must itself be
  a multiple of 32. The handler on `feat/worker` currently rounds down to 32
  (`width // 32 * 32`); it must become `// 64 * 64` (720 -> 704, 1056 -> 1024), together with its
  docstring and tests. With a 32-multiple that is not a 64-multiple (e.g. 1312) the half-size
  stage gets a size the model rounds differently, and the output size will not be what the
  sidecar reports.
* v2v `INPUT` field is `file`: the handler already does this (`INPUT_FIELDS["v2v"]`).
* Defaults: 1280x704 (720 is not a multiple of 32 or 64), 24 fps, 121 frames (~5.04 s).
* Frame count must be 8k+1 (handler already enforces it). For v2v it must also be >= 33
  (handler change pending, see V2V below).
* Size limits: the handler allows up to 2048x2048 and 481 frames. That maximum is **untested**
  (`scripts/validate-workflows.sh` only proves `/prompt` accepts it, not that 48 GB can run
  it). Recommend the UI caps resolution (for example 1280x704 and 1536x864-class presets) and length
  (about 10 s) until the real-GPU test has measured the limits.

## V2V is "continuation"

`v2v` extends your clip; it does not edit it.

* The **last K = 25 frames** of the input (about 1 s at 24 fps) are used as a guide at
  `frame_idx 0` of the new clip (`LTXVAddGuide`, strength `GUIDE_STRENGTH`, 1.0). That
  conditions the **first ~K frames of the new clip** (about 1 s) to resemble the last K frames of
  the input. **The output does not start after the input; the new segment overlaps the last
  ~1 s of the source** and then follows the prompt from there.
* **Output is the new segment only** (`FRAMES` frames). The source is not included. The guide
  frames are cropped (`LTXVCropGuides`) before the stage-1 latent is upscaled and again before
  decoding, and are re-added at full size for stage 2, as the I2V graph does with the image.
* **Joining clips:** a UI or script that concatenates source and result should drop the first
  K/fps seconds (the first K = 25 frames, about 1.04 s at 24 fps) of the new segment, or the
  last K/fps seconds of the source, to avoid a duplicated second.
* **Audio is newly generated** from the prompt; voice, music and ambience do not continue
  the source's sound (there is a seam when joined). The input's audio is ignored.
* **Not verified here:** this overlap behaviour and the visual continuity are read from the
  `LTXVAddGuide` source, not observed. Confirm on the first real GPU run.
* **K must be 8n+1** (25 or 49; anything else is cut down to the nearest 8n+1). Change it
  by editing `GUIDE_K` in `scripts/build-workflows.py` (and `GUIDE_WINDOW_S`, the number of
  trailing seconds decoded, which must cover K frames at the source frame rate; 4 s covers K=49
  down to 13 fps) and re-running the build. Larger K costs more VAE-encode time and attention
  tokens; keep it at 25 or 49.
* **v2v needs FRAMES >= 33.** The guide has to fit inside the latent, and the handler's
  minimum of 9 frames fails at run time with K=25 (`/prompt` cannot catch it; the value is only
  checked when the node runs). The UI must offer at least 33 frames for v2v, and the handler is
  to reject v2v with fewer than 33 frames (handler change, not in this branch).
* Inputs with fewer than K frames use what exists (a 12-frame clip gives a 12-frame guide, which
  `LTXVAddGuide` cuts to 8n+1 = 9; executed in `validate-workflows`).
* Only the last `GUIDE_WINDOW_S` (4 s) of the input are decoded (`Video Slice`, negative start
  time counts from the end), so memory does not grow with the input length. The last K frames
  are then taken by count (`ImageFromBatch`, index -K). A source below about 6 fps has fewer than
  25 frames in that 4 s window, so fewer guide frames are used. Selecting by count without
  decoding the whole file is not possible with core nodes, so the window stays.
* Frames are scaled to `WIDTH`x`HEIGHT` with a centre crop (aspect ratio is preserved, edges cut).

UI wording suggestion: "Continue this clip: a new video that starts from the last second
of yours (it repeats that second) and goes on from there, with new sound. Your original is
not included."

### Tuning knobs (V2V), first to try

1. `GUIDE_STRENGTH` in `scripts/build-workflows.py` (1.0). The Comfy-Org flf2v template uses
   0.7; lower values let the model move away from the source tail sooner.
2. `GUIDE_K` (25; 8n+1, e.g. 49) and `GUIDE_WINDOW_S` (4 s).

## Release checklist

1. Bump `WORKFLOW_VERSION` in `scripts/build-workflows.py` (this is the output prefix `_wfN`) and
   the `Workflow version:` line above, together; run `make -f scripts/workflows.mk build-workflows`.
2. Run `make -f scripts/workflows.mk test-workflows` and `validate-workflows` (all must pass).
3. Ship the handler change (64-rounding, v2v minimum 33 frames) and the workflow files in the same
   release; rebuild the worker image if the handler changed.
4. Sync the workflows to the volume: `scripts/download-models.sh --workflows-only`.

## Models

Filenames only (never paths); the folders come from `worker/extra_model_paths.yaml`.
Names are taken from `scripts/models.lock` (single source): five are used.

| Node | File |
|---|---|
| `UNETLoader` (`weight_dtype: default`) | `ltx-2.5-22b-distilled-transformer-comfy-int8-convrot.safetensors` |
| `CLIPLoader` (`type: ltxv`) | `gemma4-12b-with-proj-ltx-2.5-comfy-int8-convrot.safetensors` |
| `VAELoader` (video) | `ltx-2.5-video-vae-bf16.safetensors` |
| `VAELoader` (audio) | `ltx-2.5-audio-vae-bf16.safetensors` |
| `LatentUpscaleModelLoader` (two-stage only) | `ltx-2.5-latent-spatial-upscaler-x2-bf16-1.0.safetensors` |

The other `default` entries of `models.lock` (temporal upscaler, duration head, conv VAE) are
reserved and unused by these workflows. The single-stage files do not need the upscaler.

## Regenerate / edit

The JSON files are generated by `scripts/build-workflows.py` so the six graphs stay consistent.
Edit the script, then:

    make -f scripts/workflows.mk build-workflows

Hand-editing a JSON file is fine for a quick experiment (keep titles unique, keep the contract
titles), but the next build overwrites it. To design a change visually, run ComfyUI (dev pod),
rebuild the graph in the editor, export with "Save (API Format)", and port the change to the
script.

## Validate (no GPU)

    make -f scripts/workflows.mk test-workflows       # static, no docker
    make -f scripts/workflows.mk validate-workflows   # static + docker (needs the worker image)

`validate-workflows` starts ComfyUI `--cpu` from the worker image (`IMAGE`, default
`ghcr.io/ken-ck-yu/ltx25-worker:dev`) with a fake volume of zero-byte files named as in
`models.lock`, lints every workflow against `/object_info` (classes, required inputs, link
types, combo values), fills each with the handler's own `fill_workflow` for four parameter
sets (default, custom negative, minimum size, 2048x2048x481), and requires `POST /prompt` to return
HTTP 200 with empty `node_errors`. It also really executes the v2v input chain
(trim, decode, last K frames, resize) on CPU and requires exactly K frames.
The static checks also pin the loader and sampler literals (CLIPLoader `type` ltxv, UNETLoader
`weight_dtype` default, `euler_ancestral`, the sigma strings, CFG 1/1) and every link's output
slot, and run built-in negative controls (for example CLIPLoader `type: wan` must fail).
`HANDLER=` and `LOCK=` select `handler.py` and `models.lock` when they are not in this checkout.

Not provable without a GPU and the real models: image/video quality, VRAM and speed
(two-stage versus single-stage), that audio is present and not silent, int8-convrot loading
and kernels, `CLIPLoader` loading the Gemma 4 int8 file, how well the V2V guide continues a clip,
and the sampler/sigma choices (copied from the template, not tuned).
